# КАНОН · как мы ведём проекты в md

Главный файл: роли, запреты, порядок работ, указатели. Подробные правила — по темам в `kanon/pravila/` (ОД-13). Кладётся в любой новый проект, по нему ассистент разворачивает систему и работает в каждой сессии.

Версия 23 · 27.10.2026 — по документу владельца v23 (блок №3): три слоя принуждения, правила по структуре §7, шаблоны, хуки, журнал с квитанциями. Версия 3 · 27.10.2026 — «Оркестрация и дисциплина правок». Версия 2 · 27.10.2026 — «Полнота работы». Версия 1 — до 27.10.2026, без номера.

## На пальцах

1. Всё, что мы знаем о проекте, лежит в **md-файлах внутри репозитория**, рядом с кодом. В голове и в чате ничего не хранится.
2. У каждого модуля свой файл **`_ctx.md`**. Там и только там живёт правда о модуле: что он делает, что сломано, что решено, что запрещено трогать.
3. **`ROOT.md`** — общая сводка по проекту. Она **собирается автоматически** из всех `_ctx.md`, руками её не правим.
4. **Дашборд `dashboard.html`** — картинка для глаз. Тоже собирается автоматически, одной командой. Это визуализатор, не редактор.
5. Правило конвейера: **правим только md → собираем → смотрим html.** Обратного пути нет.

```
<модуль>/_ctx.md  ─┐
<модуль>/_ctx.md  ─┼─→  cargo xtask  ─→  ROOT.md + dashboard.json  ─→  dashboard.html
<модуль>/_ctx.md  ─┘        (сборщик + валидатор)
```

## Роли

- **Владелец** — ставит задачи блоками, принимает решения, снимает печати. Каждый блок — в журнале `docs/resheniya/resheniya.md` (ОД-14).
- **Главная сессия** — ведёт канон, делит задачу на листы, раздаёт их агентам, сливает только после собственного перезапуска проверок (ОД-3, ПР-14).
- **Автор реализации** — один лист, своё владение файлами; тесты не меняет (ОД-2, ОД-3).
- **Проверяющий** — читает, запускает, пишет отчёт; код не меняет (ОД-3).

## Шаблон `_ctx.md`

Шаблон — `templates/ctx.md` (разделы НАЗНАЧЕНИЕ … НЕ ТРОГАТЬ, проверяет валидатор). Если модуль и бэк, и фронт (например, веб-скринер), `_ctx.md` делится на две половины. В дашборде слои показаны раздельно: **ФРОНТЕНД** и **БЭКЕНД**.

## Три слоя принуждения (§0)

Правило в тексте канона — просьба. Агент её обычно выполняет, но под нагрузкой контекста забывает. Поэтому каждое правило канона относится к одному из трёх слоёв, и слой выбирается по цене нарушения:

| Слой | Что это | Когда |
|---|---|---|
| Текст (главный файл, `kanon/pravila/`) | рекомендация | стиль, порядок работ, форма отчёта |
| Хук | код, который блокирует или проверяет действие | всё, что нельзя нарушать: чтение закрытых данных, правка замороженных файлов, остановка без тестов |
| Права (deny-списки) | инструмент недоступен вообще | команды и пути, которые агенту не нужны никогда |

Правило канона: **если нарушение правила испортило бы результат (утечка, подмена, потеря), оно обязано быть хуком или правом, а не абзацем.** При каждой пойманной ошибке первый вопрос — «какой хук её бы не пропустил».

Хуки и права — локальные настройки инструмента разработки (в git не попадают); их перечень и какую прошлую ошибку ловит каждый — в журнале решений, блок №3. Названия инструмента в этом разделе обезличены; дословный текст — документ владельца v23 (`docs/kanon/`).

## Законы

1. **Закон канона.** Статус факта живёт только в `_ctx.md` его модуля. ROOT и дашборд — производные. При противоречии прав модуль.
2. **Закрытое только в архиве.** В живых файлах нет ✅-строк: закрыл, значит, строка уехала в `arhiv.md`.
3. **Ничего не выдумывать.** Неизвестное оформляется как `❓` в ОТКРЫТО, а не как догадка в каноне. Спорный факт несёт источник: `(лог CI)`, `(замер 23.09)`.
4. **Одна черепаха.** Одна крупная стройка за раз. Остальное ждёт в ТЕХДОЛГЕ.
5. **HTML руками не правится.** Дашборд показывает неправду? Чиним md и пересобираем.
6. **Печать — это приговор.** `Ъ —` не пересматривается без моей явной команды. Снять печать можно только записью в архиве с датой и причиной.
7. **Критерий остановки пишется заранее.** Любая гипотеза получает порог до эксперимента («меньше 0.5 bps чистыми — закрываем»). Результат записывается любым, в том числе отрицательным.

## Лимиты

- файл кода ≤ **200** строк, функция ≤ ~40
- главный файл канона ≤ **150** строк (ОД-13)
- `_ctx.md` ≤ **150** строк (разросся — делим модуль)
- модулей на уровень ≤ **10**
- задач в модуле ≤ **25**

Сборщик проверяет лимиты сам (`cargo xtask --check`), это же работает как CI.

## Ритм сессии

**Начало.** Ассистент читает `pravila.md` → `spec.md` → `ROOT.md` → `_ctx.md` нужного модуля → нужные задаче файлы `kanon/pravila/`. НЕ ТРОГАТЬ и ПЕЧАТИ — запреты.

**По ходу.**
- Одна сессия — один модуль.
- Сначала план с гейтами, потом код (ОД-8, ПР-1). Тесты обязательны.
- Нашёл баг или принял решение — сразу в `_ctx.md`, не «потом».

**Конец.**
1. Обновить `_ctx.md` затронутых модулей.
2. Закрытое перенести строкой в `arhiv.md`, решения записать печатью, вопросы — в ОТКРЫТО.
3. `cargo xtask`: пересобрать ROOT и дашборд, валидатор зелёный.
4. **Коммит.** Рабочая копия чистая.
5. **Push** в удалённый репозиторий (бэкап).
6. Контекст раздулся? Делаем `/clear`: всё важное уже в md.

## Правила по темам

Задание агенту ссылается на нужные файлы, а не на весь канон (ОД-13). `polnota.md` — в каждое задание целиком.

| Файл | Тема | Пункты |
|---|---|---|
| `kanon/pravila/polnota.md` | §1 полнота: гейты, исполнение, доказательства и отчёт, контекст | ПР-1…17, §1+1 |
| `kanon/pravila/orkestratsiya.md` | §2 оркестрация и дисциплина правок | ОД-1…10, §2+1…3 |
| `kanon/pravila/dannye.md` | §3 данные и информационное множество | §3.1…7, ОД-11, ОД-12 |
| `kanon/pravila/otbor_statistika.md` | §4 отбор, статистика, предрегистрация | §4.1…8 |
| `kanon/pravila/proverka.md` | §5 проверка кода и результатов | §5.1…5 |
| `kanon/pravila/svyaz.md` | §6 связь с владельцем | §6.1…6 |
| `kanon/pravila/mutations.md` | обязательные мутации по темам проекта, какой тест ловит | — |

## Структура канона

**ОД-13.** Главный файл канона — короткий (до 150 строк): роли, запреты, порядок работ, указатели. Подробные правила — отдельными файлами в `kanon/pravila/` по темам (полнота, оркестрация, данные, тесты, отчёты); задание агенту ссылается на нужные файлы, а не на весь канон.

**ОД-14.** Журнал решений владельца — отдельный файл только для записи (append), с номером и временем каждого блока; главная сессия подтверждает приём блока его номером. Блок без подтверждения считается не дошедшим.
